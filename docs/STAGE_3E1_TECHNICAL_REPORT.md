## Registry and allocator changes

`APPEND_PROVEN`, `PROJECT_APPENDED`, and `ENGINE_OWNED` preserve the difference
between verified archive growth, project ownership, and HG-Engine-generated
prefixes. Each append namespace stores its pristine count, actual allocation
start, small proven maximum, archive identity, and contiguous policy.

`allocate_appended_resource` verifies the exact ROM revision, selects the next
contiguous free ID across the physical collision domain, and returns a new
persistent registry value. Existing records never renumber and filesystem
order is irrelevant. Local scripts 965/966 and script headers 967/968 share
`script_narc`; common scripts use that same collision domain.

Failure tests cover unproven archives, below-boundary pins, gaps, controlled
replacement collisions, duplicate numeric ownership, exhaustion, shared
script-domain stability, wrong ROM revision, scanner disagreement, malformed
BTAF count, and missing/gapped generated members.

## Runtime lookup/source evidence

`8dcf4c981ac650ae1f4f80c926b588b06293ee0e`, `src/filesystem.c`
reads BTAF's dynamic `u16 num_files`, bounds-checks member IDs against it, and
uses indexed FAT records. Inspected map-matrix, land-data, event, script,
script-header, and message callers pass stored IDs into those APIs. No fixed
retail count was found on these paths. Numeric reference widths alone were not
accepted as proof; final conclusions require the binary and emulator evidence
above.

## Confirmed, inferred, and unknown

- dynamic BTAF-count lookup in all five world-resource paths;
- bounded contiguous append and native access at the listed IDs;
- map/event/script/header/text identity on both cells;
- native adjacency between appended map members;
- ROM repacking, movement, stability, and clean determinism.

Confirmed by source/bytes only:

- matrix 289 occupies a valid second appended position; one running field can
  naturally load only its active matrix, so 289 remains the bounded tail probe.

Inferred:

- small further contiguous windows should follow the same dynamic lookup;
  the registry deliberately does not allocate beyond the emulator-tested
  maxima.

Unknown/unsupported:

- the safe practical maximum for any archive;
- sparse append layouts;
- other NARCs or ROM revisions;
- global flag/variable capacity;
- general safety of every internal use of the truncated matrix-ID cache;
- production map-header capacity.

separate proof focused only on the fixed map-header table. It must not infer
